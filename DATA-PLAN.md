## Tested sources
### ctx.inference.complete (storyboard writing)
**Used by**: `createProject` — turns a story prompt + style into a film title and 4–6 scenes (title, one-line description, visual generation prompt)
**Test command**: `bun /opt/muse/assets/spaces/ts-runtime/dist/probe-ctx.js < /tmp/probe-inference.ts`
**Sample output**: `{"title":"What the Light Calls","scenes":[{"title":"The Nightly Vigil","description":"A solitary keeper begins his nightly ritual...","visualPrompt":"Cinematic black-and-white film still, film noir..."}, ...5 scenes total]}` — schema-validated structured output, ~16s
**Processing**: zod schema enforces title + scenes array; scene count clamped to 4–6 in the prompt; visualPrompt is stored per scene and later combined with the project's style string when generating the still.

### ctx.tool.generate_media (scene stills)
**Used by**: `generateScene` (per-scene cinematic still, landscape 16:9) and `seedSamples` (sample-film stills)
**Test command**: probe-ctx run of a snippet calling `ctx.tool.generate_media(prompt, { orientation: "landscape" })`
**Sample output**: probe mode returns `ctx.tool.generate_media is not available in probe mode — requires a built web artifact` — the SDK type (`GeneratedMedia { blobKey, url, contentType, bytes }`, own-origin `./blobs/<key>` URL, stored in this space's ctx.blobs) is the contract; it will be verified for real in Build via `artifact.invoke_action` on `generateScene` and the audit. No video generation exists in the runtime tool surface, so the player uses the brief-sanctioned fallback: generated stills with a slow cinematic pan/zoom (Ken Burns), captions, and scene sequencing.
**Processing**: prompt = scene visualPrompt + style suffix (per-style cinematic look string) + `cinematic film still, 16:9, no text`; returned blobKey persisted on the scene row; status flips pending → generating → ready/failed.

### Build-time hero image (media.generate_image)
**Used by**: landing hero — one original cinematic film-still-style image generated at build time into `client/src/assets/`, imported by the client. Not a real film still and not Flick content; an original generated illustration in a photographic cinematic style for the hero backdrop.

## Long-term data behavior
- **Refresh policy**: none — all data is user-created at runtime; no external feed.
- **Growth**: one project row per film, one scene row per scene; images live in ctx.blobs, only blob keys in the DB.
- **Ordering**: projects newest-first in "My films"; gallery shows sample films plus finished user films; scenes ordered by position.
- **Time semantics**: created_at is a creation instant, rendered viewer-local.

## Project Bible (added 2026-11-12 — the differentiator vs Flick)

User direction (verbatim): "I want to differentiate from flick by having more character development and location development" / "Build it into FilmKit now". Parent-agent brief: Flick's characters are ad-hoc reference photos and its locations are style presets; FilmKit instead gives each project a **Bible** of developed characters and locations.

- **Tables** (migration `0003_project_bible_characters_locations_scene_tags.sql`): `characters` (project_id, name, role, appearance, wardrobe, personality, backstory, image_blob_key, status), `locations` (project_id, name, description, mood, lighting, time_of_day, image_blob_key, status), `scene_characters` (scene_id × character_id link), and new `scenes` columns `location_id`, `state_note`, `last_prompt`. All follow the existing ctx.db + ctx.blobs pattern; only blob keys are persisted.
- **Actions**: `addCharacter` / `updateCharacter` / `deleteCharacter` / `generateCharacterImage` (portrait sheet from the profile + project style via `ctx.tool.generate_media`), `addLocation` / `updateLocation` / `deleteLocation` / `generateLocationImage` (establishing view), `setSceneBible` (one location, many characters, state note per scene), `developBible` (auto-develop, below). `getProject` now also returns `characters` and `locations`; `sceneOut` carries `locationId`, `characterIds`, `stateNote`, `lastPrompt`.
- **Auto-develop**: `developBible` runs `ctx.inference.complete` over the story prompt + storyboard + existing bible names and returns *drafts only* — character/location profiles plus suggested per-scene tags. Nothing is written until the user edits/accepts each draft in the review panel (accept = the ordinary add actions) or explicitly applies the suggested tags; existing entries are named in the prompt so they are not re-proposed, and tag application never clears an existing tag a suggestion doesn't resolve.
- **Generation wiring**: `generateStillForScene` composes the image prompt as before, then folds in, for tagged scenes only: the location's name/description/mood/lighting/time-of-day, each tagged character's name/role/appearance/wardrobe/personality, and the scene's state note. The composed prompt is stored on the scene as `last_prompt` and shown in the studio ("Prompt sent to the camera for the latest still"), so the folding is directly verifiable. Untagged scenes compose byte-identically to the pre-bible prompt.
- **Reference images**: `ctx.tool.generate_media`'s options are `{ orientation, key }` only (checked in the SDK types, `verticals.d.ts`) — the generation path accepts no reference images, so character portraits / location views cannot be passed as references today. They are generated and displayed as the bible's canonical look for each entry, and consistency is carried by the profile descriptors folded into every tagged scene's prompt. If the runtime later accepts references, the portrait/view blob keys are already stored and ready to pass.

## Stage 3 — Story view (2026-11-12, FEATURES.md §6)

The studio gains a **Story** section (section nav is now Story / Storyboard / Bible / Watch): a real script document per project, import, write-from-idea, plan-my-shots, and Edit with AI — on top of the Stage 1 Bible and Stage 2 shell, which are unchanged in behavior.

- **Schema** (migration `0005_stage3_story_script_document_and_scene_script_heading.sql`): `projects.script_text` (nullable — the script document; null until written/imported) and `scenes.script_heading` (nullable — the script heading a storyboard scene was planned from). `getProject` now returns `script`; `sceneOut` carries `scriptHeading`. `duplicateProject` copies both; `deleteProject` is unaffected (rows cascade by project delete as before).
- **Actions**: `saveScript` (autosave target; empty text clears to null; samples rejected), `writeScriptFromIdea` (ctx.inference over prompt + style + bible context — the same binding-context string the storyboard writer uses, factored into `loadBible`/`bibleContextString` and now shared with `storyboardFromScript`; returns a draft the user reviews and keeps — keeping routes through the normal editor save), `editScriptWithAi` (instruction + current script → full revised draft returned, **never saved server-side**; the client shows Keep/Discard and only Keep writes, via `saveScript`), `planShotsFromScript` (`mode: append | replace`).
- **Plan my shots parsing**: deterministic, no inference when headings exist. A heading is a line starting `INT.`/`EXT.`/`INT./EXT.`/`EST.` (dot-forced headings accepted, ≤120 chars) — the same forgiving regex runs client-side for the outline. One storyboard scene per script block: title = title-cased heading, description/visual prompt = the block's action lines with character cues (short ALL-CAPS lines) and the dialogue line after each cue stripped. Scenes store `script_heading`, and any Bible character/location whose name appears in the block's text is auto-tagged (location = first match), so a characters-first project's cast survives planning. No headings → fallback to the existing inference storyboard writer over the script text (bible as binding context), scenes with `script_heading = null`. Replace mode deletes the project's scenes + their tag links first; the client always asks append-vs-replace when scenes exist, so stills/tags are never wiped silently.
- **Client**: `StoryPanel` in the studio — monospace editor (native undo/redo) with 900ms-debounced autosave and a Saved/Saving/Unsaved status, word + scene counts; an outline of script headings with per-heading coverage ("On the storyboard" / "Not storyboarded yet", matched on normalized `script_heading`) and chips for Bible characters named in that block; tapping a heading (or a scene card's "View in script — INT. …" button) selects the heading text in the editor and scrolls to it. Import dialog: paste or `.txt`/`.fountain`/`.md` file upload (read client-side as text), Replace or Append chosen by the user. Home's **Script to Film** now lands on the Story section with the import dialog open (`focus: "script"` scroll target changed from the storyboard to `studio-story`). The Stage 2 `ScriptStartPanel` paste flow still works and now also files the pasted text as `script_text` when the project has none.
- **Verified in the sandbox (2026-11-12)**: characters-first project (Mara Voss + The Lantern Room) + saved 3-scene script → plan (append) created exactly 3 scenes titled from the headings, dialogue/cues stripped from descriptions, Mara auto-tagged in all 3, the location in the one scene naming it, headings stored on every scene; second append → 6; replace → back to exactly 3 with fresh ids, script + Bible untouched. Edit with AI returned a darker-ending draft while the stored script stayed byte-identical (no auto-overwrite). Write-from-idea on a prompt-only project returned a formatted screenplay (INT./EXT. headings, CAPS cues, dialogue). Prose script with no headings → fallback planned 5 scenes, `fromHeadings: false`. Test projects deleted from the sandbox afterwards.

The studio gains a **Canvas** section (section nav is now Story / Storyboard / Canvas / Bible / Watch): a per-project node board with sections, wiring, media actions, Bible-tagged generation, and an approval-gated AI chat — on top of Stages 1–3, unchanged in behavior. Voice/Music/Emotion nodes are deliberately absent: no real audio models exist until Stage 9, and FilmKit does not ship fake nodes (recorded in FEATURES.md §7).

- **Schema** (migration `0006_stage4_canvas_nodes_media_chat.sql`): `canvas_sections` (project_id, name, position, collapsed), `canvas_nodes` (project_id, section_id, type `upload|note|image|clip`, title, x/y board position, text, prompt, quantity, location_id, last_prompt), `node_characters` (node × character tags, mirroring `scene_characters`), `media_items` (project_id, node_id nullable, kind `image|upload|clip`, name, image_blob_key, prompt, favorite, archived, in_editor_bin), `canvas_links` (from_kind `node|media`, from_id, to_node_id, kind `prompt_source|start_frame`), `chat_messages` (role, text, proposal_json, proposal_status), and `projects.canvas_approval_mode` (`ask` default / `auto`). Only blob keys are persisted; `duplicateProject` does not copy the canvas or chat (documented in FEATURES.md §7 behavior); `deleteProject` removes all canvas rows.

- **Chat proposals**: `canvasChat` stores the user message, then `ctx.inference.complete` (project context: prompt, style, scene titles, bible names, node count, last 8 messages) returns a reply plus an optional structured proposal (`shotlist` | `bible` | `images`). Nothing is created while a proposal is `pending`. Applying a shot list appends storyboard scenes; applying images creates Generate Image nodes in SHOTS and runs them; applying bible drafts only flips the proposal to `in_review` — the client hands the drafts to the BiblePanel review flow (the same edit/accept/discard surface as Develop), so chat bible entries are never saved directly. In **Auto** approval mode an images proposal runs inside `canvasChat` itself and is stored already-`applied` with a note in the reply; shot lists and bible drafts still wait. All other proposal kinds in Ask mode were verified to create nothing before approval.
- **Client**: `CanvasPanel` in the studio (breaks out wider than the studio column). Desktop board: pointer-drag pan, header-drag node moves persisted via `updateCanvasNode`, zoom buttons + reset, dashed section frames computed from member bounding boxes, SVG link curves (solid = prompt source, dashed = start frame). Phone width: a stacked fallback — nodes grouped under section headings with every action reachable (called out in FEATURES.md §7). ## Stage 6 — 3D Stage (2026-11-12, FEATURES.md §8)

The studio gains a **Stage** section (section nav is now Story / Storyboard / Canvas / Stage / Editor / Bible / Watch): a per-project top-down blocking board with multiple setups, Bible-linked figures, cameras with field-of-view cones, props, a live auto-composed shot description, and sends to the canvas and storyboard — on top of Stages 1–5, unchanged in behavior. **Honest scope, stated in FEATURES.md §8: this is a blocking/planning tool — no 3D rendering engine, no video recording of the stage, no timed camera actions; a camera's free-text movement note is the whole of camera motion and it goes into the shot description.**

- **Schema** (migration `0008_stage6_stage_setups_and_items.sql`): `stage_setups` (project_id, name, position) and `stage_items` (setup_id, project_id, kind `figure|camera|prop`, nullable character_id, label snapshot, color, x/y as board percentages 0–100, rotation degrees with 0 = up/clockwise, and cameras-only shot_size `wide|medium|close`, cam_height `low|eye|high|overhead`, movement_note, description_override). Only plain values are persisted — no media. `deleteProject` removes items then setups; `duplicateProject` does not copy the stage (same as the canvas, documented in FEATURES.md §8).
- **Bible link**: figures link to characters by id but keep a **label snapshot**; `deleteCharacter` now nulls `stage_items.character_id` (and stale `node_characters` rows), so a deleted character's figure becomes a generic labeled figure — verified live: the figure kept its name, color, and position with `characterId: null`. Stage reads resolve the live character name when the link survives, so renames show up on the board.
- **Actions**: `getStage` (all setups + items, character names resolved), `addStageSetup` / `renameStageSetup` / `deleteStageSetup` (items cascade manually), `addStageCast` (one figure per Bible character not already placed, colors from a fixed 8-color palette by cast order), `addStageItem` (generic figure / camera with wide+eye defaults / prop with preset or custom label), `updateStageItem` (position, rotation, label, color, camera settings, movement note, description override — null clears), `deleteStageItem`, `sendStageToCanvas`, `sendStageToStoryboard`. All mutations reject samples via `assertWritable`.
- **Shot geometry** (identical math server- and client-side, so the live text is the sent text): a camera frames a figure/prop when it is in front of the camera and inside the shot-size cone (half-angles 35°/25°/14° for wide/medium/close); side is frame left / center / frame right from the lateral ratio (±0.28), depth is foreground / mid-ground / background from board distance (<24 / >52). The description reads e.g. "Medium shot, at eye level. Jack Rye is at center frame, in the foreground; Mara Voss is at frame left, in the background. Also visible: Table in the background at center frame. Camera movement: slow push-in." A stored `description_override` wins over the auto text at send time.
- **Sends**: `sendStageToCanvas` creates a Generate Image node in the SHOTS section whose prompt is the effective description with the **framed** cast's Bible profiles folded in, in the exact `Character Name (role): …` shape scene generation uses, and tags the node via `node_characters` with the framed characters. `runImageNodeInternal` gained a dedupe guard (a bible part already present in the prompt text, matched by its `Character Name (` / `Setting: Name —` lead, is not folded twice), so running a stage-sent node composes cleanly. `sendStageToStoryboard` appends a scene (title = "Setup — Camera", description/visual prompt = the effective description) and tags it with the framed cast via `scene_characters`.
